# sag-setup — first-run setup (manual trigger only)

This skill **does not load itself**. It runs when the user types `/sag-setup` or gives a
direct order to set the plugin up. It logs in, can create a SAG source, and writes config
files — do not infer permission for any of that from an unrelated request.

## Ask for these, in this order

Stop and ask. Do not guess a URL, invent a source name, or pick include globs by reading
the repo without confirmation.

| # | Ask | Needed when | Example |
|---|---|---|---|
| 1 | **SAG URL** | always | `http://sag.home` |
| 2 | **Login name** | always | `vuong` |
| 3 | **Is there already a scope to join?** | always | see below |
| 4 | **`source_id`** | JOIN only | `a3f1…` or the name to look up |
| 5 | **Source name** | BOOTSTRAP only | `project-a-knowledge` |
| 6 | **State service URL + token** | only if agents run on >1 machine | `http://state.home:9000` |

Question 3 decides everything after it. Phrase it concretely: *"Has any other agent or
machine already published knowledge for this project into SAG — do you have a
`source_id`?"*

- **They have a `source_id`** → JOIN. Nothing is created. The scope already has documents,
  a manifest, and possibly a shared state service.
- **They do not** → BOOTSTRAP. This machine provisions the scope.

Everything else is derived — never ask for it:

- `key_format` comes from probing the instance (below), not from a preference.
- `source_id` in JOIN mode comes from the user; in BOOTSTRAP from `source create`.
- The read MCP url is generated by `adapter-emit`; never hand-write it.
- The write token is never asked for, shown, or pasted anywhere.

---

## Step 1 — engine (both modes)

```bash
python scripts/install-shim.py
```

Then follow its PATH instructions. It deliberately does not edit PATH itself.

## Step 2 — probe the instance (both modes)

Do this **before** creating anything. `key_format` decides every document key, and SPEC
§S2 locks the default to `flat` on the strength of one instance's behaviour — it says in
as many words to re-verify before provisioning a new source.

Mint a token to probe with (this prints it instead of saving it):

```bash
sagctl login --url <SAG_URL> --name <name> --print-token
```

```bash
sagctl setup probe --url <SAG_URL> --token <token>
```

Read `key_format` out of the JSON and use it verbatim in the manifest. **If it comes back
`path` rather than `flat`, say so out loud** — it means this instance behaves differently
from the one the defaults were locked against, and the user should know.

Add `--full` if the user can spare a few minutes: it also measures delete semantics (S4 →
replace strategy) and MCP read scoping (S17). Without it those two are reported as
unmeasured rather than assumed.

Skipping this step fails **silently**: keys stop matching, `find_existing_by_key` never
finds the previous document, and every publish adds a duplicate instead of replacing.

## Step 3 — tokens (both modes)

Two logins, because the read and write tokens live in different places (§S12):

```bash
sagctl login --url <SAG_URL> --name <name>
```

That saves the **write** token to `~/.sagctl/credentials.json` (0600). It must never
enter the agent's environment.

```bash
sagctl login --url <SAG_URL> --name <name>-read --print-token
```

That prints the **read** token; the user puts it in `SAG_READ_TOKEN`, along with
`SAG_URL`.

> Be honest about what this split buys. SAG's JWT carries no role or scope, and there is
> no isolation between identities (S11). The read token can write. Splitting them limits
> the blast radius of the agent-side token leaking; it does not limit what a leaked token
> can do. Do not describe the read token as read-only.

## Step 4a — BOOTSTRAP: provision the scope

```bash
sagctl source create "<source name>"
```

Write `.sag-sync.json` at the repo root from `examples/sag-sync.example.json`, filling in
the `source_id` just returned and the `key_format` from step 2. Confirm the `include`
globs with the user rather than inferring them.

**Leave `deny_paths`, `ask_paths`, and `criteria` empty**, and tell the user to fill them
in themselves in a separate, reviewed commit. Per §S1 those are policy: editing them is a
distinct commit plus an audit entry plus a permission ask. This skill scaffolds a manifest
once; it is not a policy editor, and neither is any later session.

Commit the manifest — publishing needs it to be an ancestor of the file being published.

## Step 4b — JOIN: attach to an existing scope

Nothing is created. Confirm the scope first:

```bash
sagctl document list <source_id>
```

Seeing the other agent's documents is the confirmation that the `source_id` is right.

Then, for the manifest — two cases, and the difference matters:

- **Same repo** as the agent that set it up: `.sag-sync.json` is already there, in Git.
  Do nothing. This is the good case.
- **Different repo**: create one declaring the *same* `source_id`. **`key_format` must
  match the existing manifest exactly.** If the existing scope uses `flat` and the new
  manifest takes a different value, the same file yields a different key and publishing
  creates a duplicate instead of replacing. Check it, do not assume.

  Also keep the directory prefixes disjoint from the other repo's (`research/` vs
  `docs/`), and tell the user that `maintain`'s orphan and stale-branch detection is
  defined relative to one repo's Git HEAD — running a prune from either repo will flag the
  other's documents. Propose-only, but do not act on it.

## Step 5 — wire this agent tool (both modes)

Run from inside the repo so `source_id` is read from the manifest:

```bash
sagctl adapter-emit claude-code --write .
```

For the other tools, `sagctl adapter-emit hermes|codex --plugin-root <path>`. Merge the
printed `settings.json` / `config.yaml` / `config.toml` blocks by hand — the command
refuses to clobber files that hold unrelated settings.

## Step 6 — more than one machine?

Only if the user said yes to question 6. One state service for the fleet, so the cost cap,
the queue, and the audit log are shared rather than one private copy per host:

```bash
export SAGCTL_STATE_URL="http://<state-host>:9000"
```

```bash
export SAGCTL_STATE_TOKEN="<shared secret>"
```

If this is a JOIN and the other machine ran with local state before the service existed,
its history is still on that machine's disk. The layouts are identical, so migrating is a
directory copy of `~/.sagctl/<sha256(source_id)[:12]>/` into the service's home. Skipping
it costs nothing functionally — `doctor --unassessed` will just list files the other agent
already assessed.

## Step 7 — verify, and say what is still unverified

```bash
sagctl doctor
```

Check three things and report them plainly:

1. `state.backend` — `local` means this host does **not** share the cap/queue/audit with
   other hosts. Correct for a single machine, a bug for a fleet.
2. The generated `.mcp.json` url carries `?source_id=` — otherwise this agent can read
   every project on the instance.
3. `sagctl publish-status <source_id> <key>` finds a document the other agent published
   (JOIN), or a test publish round-trips (BOOTSTRAP).

Then close by stating what was **not** measured. If step 2 ran without `--full`, the
replace strategy and MCP read scoping are assumptions, not results. Do not report a setup
as fully verified when two of its defaults were never tested against this instance.
